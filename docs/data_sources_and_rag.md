# 数据来源、工具调用与可追溯检索

本轮选择：沿用现有 `ToolSpec → ToolCall → ToolResult` 工具调用，增加本地原文快照与 SQLite FTS5/BM25 检索。没有另接一套 Agent 框架，也没有安装向量数据库。选择依据是融资额、公司名、日期、收入指标等需要精确定位，当前资料规模较小；先验证关键词检索和证据引用，再判断是否需要向量召回。

## 实际数据流

1. `web_search` 找线索，只返回摘要和来源；摘要不进入原文证据库。
2. `fetch_url` 读取公开网页/文字型 PDF，归档清洗后的完整提取正文；给模型的首段限制为 10,000 字符，长文余下部分由 `read_source` 读取。
3. `KnowledgeStore.archive` 保存原 URL、标题、首次归档 UTC 时间、正文 SHA256 和稳定快照 ID。同 URL 内容变化保留新版本；同内容复用原快照。哈希只证明本地版本一致，不证明网站披露真实。
4. 原文按段落分块，超长段落每 1,500 字符切分；保存原始字符起止位置。`search_knowledge` 用 BM25 返回最多五个原文块，`read_source` 指定快照和分块读取。
5. 工具实际返回的片段进入读取记录。验证摘录时只接受相同来源、实际已返回的连续原文；数据库里存在但模型没读到的内容不能充当已读证据。证据记录附快照 ID、哈希、时间和位置。
6. 当前融资、上市状态和最新经营数据须再查最新披露；历史快照只支持对应时点的事实。抓取时间与披露日期、数据期间分别处理。
7. 上传 BP 留在本次运行的 DocumentStore 和结果读取记录中，不自动加入跨运行的公共来源库。

默认公共来源库：`data/sources.sqlite3`，由 `Settings.knowledge_path` 配置。该文件需随研究记录保留，删除后可读结果 JSON 中当时实际返回的正文，但不能再检索未返回的归档全文。原始 PDF 二进制、网页截图和 OCR 尚未保存；本轮可追溯的是提取文本快照。网页工具没有 PDF 页级定位，因此不能自动确认在线 PDF 的指定页码引用；可用原 URL、快照和字符位置，或上传 PDF 按页读取。

## 如何修正报告

- 有可靠原文：纠正主体、产品、时间、金额、币种和统计口径，再重做受影响的分析、排序与决策。
- 只有公司原文：保留“据公司披露”的明确归属，不升级为独立证实。
- 补查后仍无依据：删除该事实及依赖推论，完整原话和处理原因留在内部台账。不能用一个猜测数字替换另一个。
- 修正后逐条复查一次；仍有明确错误或缺少支持的关键事实时记入未解决清单，只输出研究稿，不输出正式报告。每批核查最多 8 条，不代表全文准确率。
- 正式 `report.md` 与内部 `audit.md` 分离。报告保留来源、假设、公司披露和“未披露”等客观说明；内部核查状态、修正前后记录、失败原因和用量进入审计文件及 `result.json`。

摘录匹配、跨模型核查和多空辩论都不能保证语义正确。数值核对能阻止原文1百万而主张10百万这类错误，但不推导单位转换，也不能判断同一数字的主体是否正确。当前使用的机制是“原文检索 → 同源摘录与数字核对 → 关键主张独立核查 → 更正传播 → 复查”。向量召回、重排序器、GraphRAG 和全站爬虫暂不接入：目前没有检索漏召回的实测收益来支持这些复杂度。

实际链路验证：`outputs/evaluation/source_trace_20261030_021012/summary.json`；从世界银行公开接口抓取301字符原文，保存SQLite后在HTTP禁用条件下检索回读，哈希一致、同源摘录通过。这个结果只验证数据链路，不证明投资分析准确率。
